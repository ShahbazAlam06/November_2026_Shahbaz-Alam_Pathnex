Site Reliability Engineering (SRE)
Definition: SRE is a practice that uses software engineering to manage infrastructure and operations problems. Its main goal is to make applications reliable, available, scalable, and highly performant.

1. Objectives of SRE
- Improve application reliability and availability.
- Automate manual tasks.
- Reduce downtime and failures.
- Improve incident response.
- Balance new feature development with system stability.
=================
2. Key Components of SRE
1. SLI, SLO and SLA
- SLI: Actual measurement (e.g., request success rate).
- SLO: Target reliability (e.g., 99.9% uptime).
- SLA: Agreement with customers, including penalties if targets are not met.

2. Incident Management
- Detect and resolve production issues.
- Find the root cause.
- Conduct blameless postmortems to prevent recurrence.

3. Monitoring and Observability
- Monitor application and infrastructure health.
- Use dashboards, logs, metrics and alerts.

4. Automation and Toil
- Toil means repetitive manual work.
- SRE automates deployments, monitoring and routine tasks.

5. Capacity Planning
- Plan CPU, RAM, storage and servers for future traffic.
- Ensure performance and scalability.

6. Change Management
- Safely deploy production changes.
- Use CI/CD, Canary deployments and Rollbacks.

7. Reliability Engineering
- Design systems to handle failures.
- Use Chaos Engineering to test system resilience.

4. SRE Mindset
- Blameless culture: Focus on fixing problems, not blaming people.
- Automation first: Reduce manual work.
- Collaboration: Work with developers and operations teams.
- Engineering approach: Solve operational problems through code.
=================================
5. Five W's in SRE
W	Meaning
What	What is the issue?
Why	Why did it happen?
Where	Where is the issue occurring?
When	When did it happen?
Who	Who is affected?
===========================================
6. Hard Freeze vs Cold Freeze
Hard Freeze	Cold Freeze
No changes allowed.	Only essential changes allowed.
No deployments or configuration changes.	Security patches and critical fixes allowed.
Used during high-risk events.	Used when minimizing changes.

Example:
- Hard Freeze: No deployments during Black Friday.
- Cold Freeze: No new features, but critical security patches are allowed.
7. Error Budget in SRE
Definition: Error Budget is the maximum acceptable downtime or failure within a given period based on the SLO.

Formula:
    
Error: Budget = 100\% - SLO
   

Example:
- SLO = 99.9% uptime
- Error Budget = 0.1%
- Monthly downtime allowance = 43.2 minutes (30-day month).
If the application experiences 30 minutes of downtime:
- Total budget = 43.2 minutes.
- Used = 30 minutes.
- Remaining = 13.2 minutes.
What happens when the error budget is exhausted?
- Pause risky deployments.
- Focus on fixing production issues.
- Improve system reliability.
Error Budget Burn Rate:
- Fast burn = Quickly consuming the error budget; prioritize stability.
- Slow burn = More flexibility for new deployments.
